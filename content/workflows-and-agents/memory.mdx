Per [Packer et al., "MemGPT: Towards LLMs as Operating Systems" (arXiv:2310.08560, 2023)](https://arxiv.org/abs/2310.08560), virtual context management draws inspiration from hierarchical memory systems in traditional operating systems, using function calls so the LLM agent can read/write external data sources, modify its own context, and choose when to return control. That's the theoretical grounding for why agent memory needs tiers at all: an agent pages information between the context window (fast memory) and external storage (slow memory), the same way an OS pages between RAM and disk. Its open-source descendant, [Letta](https://www.letta.com/) (formerly the MemGPT project itself), implements this paging model as a standalone product, if you'd rather not build the tiering yourself.

<Callout type="warn">
  **Deprecation to lead with.** `ConversationBufferMemory` — the class most existing tutorials and older code still reference — was deprecated in LangChain v0.3.1 and is scheduled for removal at v1.0.0. The current replacement path is a checkpointer for in-thread session history, plus a Store for cross-thread, user-scoped long-term facts. Same situation as the `create_react_agent` migration note in [ReAct Agent](./patterns/react-agent) — anyone following an older tutorial will hit this deprecated class first.
</Callout>

## Core concepts

Per [LangChain/LangGraph's memory concepts doc](https://docs.langchain.com/oss/python/concepts/memory), humans use memories to remember facts (semantic memory), experiences (episodic memory), and rules (procedural memory) — and AI agents can use memory the same way.

- **Semantic memory** — durable facts about a user or domain.
- **Episodic memory** — past experiences the agent can draw on.
- **Procedural memory** — rules governing the agent's own behavior.
- **Short-term vs. long-term architecture** — short-term memory is thread-scoped, tracked as part of the agent's state and persisted via a checkpointer, updating as the graph is invoked. Long-term memory is saved within custom namespaces, shared across conversational threads, and recalled in any thread via a Store.
- **The one rule that prevents most memory bugs**: never conflate the store and the checkpointer — use the store for user facts and the checkpointer for conversation turns. Persisting transient conversation state as if it were a durable fact (or vice versa) is the exact mistake that causes memory bugs in practice.
- **Procedural memory is the odd one out** — semantic and episodic memory are both "declarative": things you can explicitly recall and state. Procedural memory is implicit — it shows up as how the agent behaves, not as a retrievable fact. In practice, this usually just means a system prompt or set of instructions that gets self-updated over time via reflection, not a separate storage mechanism in the same sense as the other two.

## Implementing each memory type

<Steps>
<Step>

#### Short-term memory via a checkpointer

- **Action**: Configure a checkpointer and let the graph persist state as part of normal invocation.
- **Result**: Conversation turns within a single thread survive across steps, without any of it leaking into other threads or users.

</Step>
<Step>

#### Long-term semantic memory via a Store

- **Action**: Write durable facts (user preferences, domain knowledge) into a Store under a namespace scoped to the user or entity they belong to.
- **Result**: Facts persist across threads and are recalled in any future thread for that namespace — the durable-fact half of the store/checkpointer split.

</Step>
<Step>

#### Long-term episodic memory via LangMem

- **Action**: Use [LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) to extract episodic memories from past interactions.
- **Result**: Be precise about what this actually stores — LangMem implements episodic memory as few-shot examples derived from past successful interactions, not raw transcripts. "Episodic memory" gets used loosely elsewhere to mean full conversation logs; here it specifically means curated examples of things that worked.

</Step>
<Step>

#### Procedural memory via prompt self-updates

- **Action**: Let the agent revise its own system prompt or instructions over time based on reflection on what did or didn't work.
- **Result**: The agent's behavior improves without a distinct "procedural memory store" — the mechanism is just an evolving prompt, not a new storage layer.

</Step>
<Step>

#### Choose Store Managers vs. Memory Management Tools

- **Action**: In LangMem, decide between Store Managers (automatically persist extracted memories in the background) and Memory Management Tools (give the agent direct, on-demand access to memory operations).
- **Result**: Store Managers suit passive, always-on capture; Memory Management Tools suit cases where the agent itself should decide what's worth remembering.

</Step>
</Steps>

<Callout type="warn">
  Common mistakes to check for:
  - **Still reaching for `ConversationBufferMemory`** from an older tutorial — it's deprecated as of v0.3.1 and being removed at v1.0.0.
  - **Conflating the store and the checkpointer** — durable facts belong in the store, conversation turns belong in the checkpointer.
  - **Treating episodic memory as raw transcript storage** rather than curated few-shot examples of past successful interactions.
  - **Expecting procedural memory to be a distinct storage system** — in practice it's the agent rewriting its own prompt, not a separate mechanism like the other two types.
  - **Skipping namespacing** on long-term memory — without it, facts leak across users or threads that should stay isolated.
</Callout>
